PERSON 2

AI/ML, Hemoglobin Estimation & Evaluation

24-hour hackathon • Deliverable implementation plan • Source-aligned to Anemia Screening Hackathon Project Guide

Operating principle: fork-and-graft the existing RAHULPATEL2002/anemia-detection Flask application; do not rebuild the full stack from scratch.

Mission

Own the model/inference/evaluation workstream. Adapt the EfficientNet-B3-based scaffold rather than starting a model from scratch; aim for joint anemia classification and continuous hemoglobin regression, and report only metrics that the available labelled data and time actually support.

Source-aligned requirements

The source repository’s existing head is binary classification; continuous Hb regression in g/dL is a required architectural change, not an existing guaranteed capability.

Use a dual-head design: classification probabilities plus a positive continuous Hb estimate. Fuse the visual embedding with Person 1’s colorimetric features and body-part encoding if feasible.

The guide proposes a weighted joint loss: L_total = 0.7 × L_CE + 0.3 × L_MSE, inverse-frequency class weighting, and accuracy-first early stopping. Treat these as starting settings to validate, not guaranteed optimal values.

Evaluation must go beyond accuracy: MAE/RMSE for Hb regression, calibration diagnostics for probabilities, confusion matrices/sensitivity/specificity, and Bland–Altman bias/95% limits of agreement when paired Hb predictions and laboratory measurements are available.

Implementation checklist

Keep binary classification and Hb regression outputs separate; do not derive a numeric Hb value from a class label.

Use patient-level split manifests from Person 1. Prevent image-level leakage and do not use the test split for early stopping or calibration.

Report the actual dataset sizes and actual achieved metrics; do not reuse published repository metrics as if they were this team’s results.

If the labelled data cannot support regression within 24 hours, preserve the working classifier and clearly mark Hb regression as unvalidated/unavailable rather than fabricate a result.

Grad-CAM is an explanatory visualization, not proof that the model is clinically correct.

Acceptance criteria

The inference interface returns a structured response on a valid sample and a useful error/warning on invalid input.

Any Hb estimate shown is generated by the implemented regression head and labelled with appropriate limitations.

Metrics are computed on a held-out, leakage-aware test split when labels permit; validation and test data are not conflated.

Calibration and Bland–Altman diagnostics are shown only when methodologically supported by available data.

Definition of done and handoff

Commit working code to the agreed branch and include a short README section with setup/run instructions.

Provide one reproducible test or example input and record observed output; never label mock output as a real model result.

Tell the integration owner what is implemented, what is incomplete, known limitations, and exact files changed.

Do not claim clinical diagnostic performance without evaluation against laboratory-measured hemoglobin and a leakage-safe test set.

Scope guardrails from the source guide

Do not build a native Android/iOS app; use the existing mobile-responsive web application.

Do not train U-Net/Mask R-CNN from scratch, attempt INT4 quantization, train GAN/diffusion augmentation, or deploy PyTorch inference as Vercel serverless functions.

Treat dual-modality eye+nail fusion, the high-sensitivity toggle, leakage audit badge, and PWA as stretch goals only after the end-to-end core works.

The system is a screening aid/prototype, not a substitute for confirmatory CBC testing or professional clinical judgment.
